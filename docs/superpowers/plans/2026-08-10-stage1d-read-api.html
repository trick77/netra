Stage 1D — the Read API

2026-08-10 · branch stage1d-read-api · one PR · closes Stage 1

Goal: make the twenty collectors' data readable by something other than psql. Every endpoint but one is a straightforward projection; /metrics is not, and it is specified first because the rest depends on nothing.

The load-bearing decision. With step omitted the hub picks a storage tier. A client that cannot tell 1h buckets from raw samples will draw them on the same axis and be wrong without ever erroring. The response therefore names the tier and makes the confusion structurally impossible — see “Why column arrays”.

Capabilities are not decoration

GET /hosts/{id} returns hosts.capabilities verbatim. This is how “this host has no hwmon” is told apart from “the sensors collector never ran”. Without it every NULL in every other response is ambiguous in exactly the way the agent went to trouble to avoid, and the read API would quietly undo a decision the collectors already paid for.

  "warnings": ["the 5m tier materialises with a 10m lag; window.to was clamped"],
  "key_columns": ["core"],
  "columns":     ["busy_avg", "busy_max"],
  "series": [
    { "key": {"core": "0"}, "points": [[1754800000000, 4.1, 9.7], …] }

Why column arrays

At the raw tier the column is busy. At 5m it is busy_avg and busy_max. The names differ per tier by construction, so a client that ignores tier still cannot silently plot a 1h mean as if it were a 60s sample — it gets a key it does not recognise instead of a number that looks fine. Every family inherits the property: cpu_total → cpu_total_avg/cpu_total_max, used → used_avg/used_max. Row arrays keep it compact for the chart the UI will draw; the header carries the names once.

Why two windows

window is what the response actually covers; requested_window is the echo. They differ at both edges, and each difference is a real fact the client must not have to guess:

  • Leading edge — retention. window.from = max(requested.from, now − retention(tier)). A from older than the tier's retention does not error; it returns the part that still exists and says so.
  • Trailing edge — materialisation lag. Every continuous aggregate in 0001_init.sql is materialized_only = true (verified against TimescaleDB 2.29.1), so the 5m tier is fresh only to now − 10m and the 1h tier to now − 1h — the end_offset of each refresh policy. window.to is clamped to that horizon.

The SQL is clamped to window, not to the request, which buys a contract worth having: a missing point inside window means the host reported nothing — never that the hub lagged. Raw tiers have no materialisation lag and are clamped on the leading edge only.

Tier selection

Retention on from, not span. Span alone gets the raw-only families wrong.

tiers(family)              // fine → coarse, per family
pick the FIRST tier T where now - from <= retention(T)
if none                    // from predates even the coarsest
    use the coarsest, clamp window.from, warn
FamilyTiersRetention
host, agent, cpu_core, disk_io, sensor, net, collector, container, filesystemraw, 5m, 1h7d / 30d / 90d
smartraw only90d
processraw only48h

The two raw-only families are why the rule is per-family: family=smart&from=60d ago must answer raw despite a span far past 7 days, because there is no 5m tier to fall back to — and family=process can never cover more than 48h whatever is asked.

Explicit step

step is a Go duration. It selects the coarsest tier whose own step is ≤ the request, so step=10m resolves to 5m rather than 400ing on a value that is not a tier. Below 60s it clamps to raw; a family without that tier clamps to its finest. step_s in the response is always the tier's real step, never the request's. An explicit step overrides range-based selection but not the window clamps — asking for raw over 60 days returns 7 days of raw and says so.

Boundary cases, written first

  1. A range straddling 7 days — from = 7d+1m ago, to = now → 5m, deterministically, on the from edge not the midpoint.
  2. A range longer than raw retention but wholly inside it… is impossible, and the test says so: span ≤ age always.
  3. from older than every tier's retention (100d) → 1h, window.from clamped to now−90d, one warning.
  4. family=process&from=7d ago → raw, window.from clamped to now−48h.
  5. from > to → 400. to in the future → clamped to now.
  6. Unknown family → 400 naming the valid ones.

Selection is a pure function over (family, from, to, step, now), so all of the above are table tests with no database. Two integration tests then pin the Go constants to the schema: every policy_retention interval must equal the tier's declared retention, and every policy_refresh_continuous_aggregate end_offset must equal its declared lag. Editing 0001 without editing the selector fails the build.

Filesystem fullness

used and free do not sum to total — the gap is the root reserve, which is neither. The read API therefore exposes used, free and total and computes no percentage at all. Any consumer's fullness is used / (used + free), as df's Use%. A percentage at the 5m or 1h tier would be worse than absent: used_max / (used_max + free_min) is a worst-case composite of two different instants, not the maximum of the true ratio.

Folded in

1 · Retention for the discrete-event tables

systemd_unit_events, package_events and — the same problem, unasked — events are plain tables with no retention. Sizing assumed “a unit changes state a handful of times a month”, which stopped holding when agents began emitting a failed-unit baseline on restart: a crash-looping agent writes to a table nothing prunes.

Decision: prune, do not hypertable-ise. Converting costs the composite foreign keys, moves every pinned policy count, and buys chunk-drop performance these row volumes do not need. Instead a CREATE OR REPLACE PROCEDURE netra_prune_discrete_events plus a daily add_job, horizon 90 days to match the 1h tier. add_job has no if_not_exists, so it is guarded by a DO block that checks timescaledb_information.jobs — 0001 must stay individually re-runnable. The job's proc_name joins the two policy names unschedulePolicyJobs already suppresses, so it cannot deadlock the suite the way #26 fixed.

2 · Coverage floors

Raised off 75%, deliberately, as the plan said to once the collector packages landed. Set from the measured number after this PR is green, one to two points under it — the gate's 0.05 grace is float-formatting slack, not headroom.
